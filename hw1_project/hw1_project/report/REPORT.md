## 1.2 공통 자료 구조와 인터페이스

세 알고리즘을 동일한 조건에서 비교하기 위해 모든 입력 데이터를 다음과 같은 `Record` 구조체로 표현하였다.

```c
typedef struct {
    int key;
    int id;
} Record;
```

- `key`: 실제 정렬 기준
- `id`: 입력 당시의 순서를 기록하기 위한 값

`id`를 별도로 저장한 이유는 안정성(stability)을 실험하기 위해서이다. 두 레코드의 `key`가 같을 때 정렬 전후의 `id` 순서가 유지되면 안정 정렬로 판단한다.

세 정렬 함수는 다음과 같은 동일한 형태를 사용한다.

```c
typedef void (*SortFunction)(Record *a, int n, SortStats *stats);
```

따라서 `main.c`는 정렬 알고리즘의 내부 구현을 알 필요 없이 동일한 방식으로 세 알고리즘을 호출할 수 있다.


## 1.3 측정 지표와 측정 방법

수업에서 중요하게 다룬 비교 횟수와 이동 횟수를 포함하여 다음 항목을 측정하였다.

| 항목 | 측정 방법 |
|---|---|
| 실행 시간 | 정렬 함수 호출 직전과 직후의 CPU 시간을 측정 |
| 비교 횟수 | 두 `Record`의 `key`를 비교할 때마다 1회 증가 |
| 이동 횟수 | `Record` 하나의 대입이 발생할 때마다 1회 증가 |
| 정확성 | 정렬 후 모든 인접 원소가 오름차순인지 검사 |
| 안정성 | 같은 `key`를 가진 레코드의 `id` 순서가 유지되는지 검사 |
| 재귀 깊이 | 퀵 정렬의 재귀 호출 깊이를 기록 |

특히 이동 횟수는 알고리즘마다 `swap`의 구현 방식이 달라질 수 있으므로, 본 실험에서는 `Record` 하나의 대입을 1 move로 정의하였다. 따라서 총 3번의 이동으로 이루어진 swap은 3 moves로 계산된다.

## 1.5 정확성 및 안정성 검증

### 정확성

정렬 후 다음 조건을 모든 인접 원소에 대해 확인하였다.

```c
key[i-1] <= key[i]
```

또한 입력 크기 `0`, `1`, `2`, `10`, `100`에 대해 별도의 정확성 테스트를 수행하였다.


### 안정성

다음과 같이 동일한 `key`를 가진 여러 레코드를 생성하였다.

```text
(key=2, id=0)
(key=1, id=1)
(key=2, id=2)
(key=1, id=3)
```

예를 들어 정렬 후 `key=1`인 원소의 `id`가 `1 → 3`, `key=2`인 원소의 `id`가 `0 → 2`와 같이 원래 순서를 유지하면 안정적인 것으로 판단한다.

원래는 입력을 한 번 하였는데 다시 같은 방식으로 데이터를 입력해서 안정성을 평가하는 것만으로는 부족할 수 있다는 점을 여러 LLM(Gemini 등)과의 검토에서 지적받았다.

따라서 한 번의 입력에서 우연히 안정적으로 보이는 것을 방지하기 위해 동일한 방식의 중복 키 데이터를 여러 번 생성하여 안정성을 확인하였다.


# 2. 알고리즘 상세

## 2.1 삽입 정렬

삽입 정렬은 배열의 앞부분을 이미 정렬된 부분으로 보고, 다음 원소를 그 위치에 삽입하는 방식이다.

### 핵심 특징

- 최선: `O(n)`
- 평균/최악: `O(n²)`
- 공간: `O(1)`
- 안정성: stable
- 이미 정렬된 데이터에 매우 적은 작업이 필요하다.

이번 구현에서는 `>` 조건으로 원소를 이동시키므로 같은 `key`를 가진 원소의 상대적인 순서를 바꾸지 않는다.


## 2.2 퀵 정렬 - 강의안의 partition을 이용한 구현

퀵 정렬은 `partition`을 이용하여 pivot을 기준으로 작은 값과 큰 값을 나눈 후 양쪽 구간을 재귀적으로 정렬한다.

구현에서는 강의안의 `partition`, 비교 횟수, 이동 횟수의 측정 방식을 참고하되, 양쪽 구간을 모두 재귀적으로 처리하여 전체 배열을 정렬하였다.

이번 실험에서 사용한 퀵 정렬 파일은 다음과 같다.

- `quick_sort.c` : 난수 pivot
- `quick_sort_first.c` : 첫 원소 pivot
- `quick_sort_middle.c` : 가운데 원소 pivot
- `quick_sort_median3.c` : 첫, 가운데, 마지막 원소의 median-of-three pivot

모든 파일은 같은 partition 구조와 `SortStats` 측정 방식을 사용한다.

### 핵심 특징

- 평균적인 경우: `O(n log n)` (난수 pivot 사용 시 기준)
- 최악의 경우: `O(n²)`
- 재귀 스택: 평균적으로 `O(log n)`, 최악의 경우 `O(n)`
- 일반적인 in-place 구현에서는 unstable.


### Pivot 선택 방법

이번 실험에서는 동일한 퀵 정렬의 partition 구조를 유지하고 pivot 선택 방법만 변경하였다.

#### 1. Random Pivot

각 partition마다 pivot의 위치를 난수로 선택한다.

난수 pivot을 사용하면 특정 입력에서 항상 나쁜 pivot이 선택되는 상황을 피할 수 있다.

#### 2. First Pivot

현재 정렬 구간의 첫 번째 원소를 pivot으로 사용한다.

강의안의 기본 Quick Sort 코드에서 사용하는 방식이며, 이미 정렬된 입력에서는 pivot이 매번 최솟값 또는 최댓값이 되어 최악의 경우가 발생할 수 있다.

#### 3. Middle Pivot

현재 정렬 구간의 가운데 원소를 pivot으로 사용한다.

이미 정렬된 입력에서는 첫 원소를 pivot으로 사용하는 것보다 균형 잡힌 분할을 만들 수 있다.

#### 4. Median-of-three Pivot

첫 번째, 가운데, 마지막 원소 중 중앙값(median)을 pivot으로 선택한다.

단순히 첫 번째 원소를 선택하는 것보다 입력의 양 끝에 치우친 pivot 선택을 줄이는 것을 목적으로 한다.


## 2.3 힙 정렬 — AI를 통해 학습한 알고리즘

힙 정렬은 완전 이진 트리 형태의 힙(heap) 자료구조를 이용하는 비교 기반 정렬 알고리즘이다. 최대 힙을 만들면 루트에 현재 구간의 최댓값이 위치한다. 이후 루트와 마지막 원소를 교환하고 남은 구간에 대해 다시 heapify를 수행한다.

### 최대 힙의 조건

부모 노드의 `key`가 자식 노드보다 크거나 같으면 최대 힙이다.

배열로 저장하면 다음과 같이 표현할 수 있다.

```text
parent = (i - 1) / 2
left   = 2i + 1
right  = 2i + 2
```

### 힙 정렬 과정

1. 입력 배열을 최대 힙으로 구성한다.
2. 루트에는 현재 힙의 최댓값이 위치한다.
3. 루트와 마지막 원소를 교환한다.
4. 힙의 크기를 1 감소시킨다.
5. `sift down / heapify`를 수행하여 다시 최대 힙을 만든다.
6. 힙 크기가 1보다 클 때까지 위 과정을 반복한다.
7. 오름차순 정렬이 완료된다.

힙을 구성하는 단계는 전체적으로 `O(n)`이고, 최댓값을 하나씩 꺼내는 과정이 `n`번 반복되며 각 단계에서 최대 `O(log n)`의 heapify가 필요하므로 전체 시간복잡도는 `O(n log n)`이다. 추가 배열 공간은 `O(1)`이며, 일반적인 힙 정렬은 안정적이지 않다.


### AI 학습에서 이해한 핵심

힙 정렬을 처음 접했을 때 중요한 부분은 정렬을 위해 매번 전체 배열을 탐색하는 대신, 힙의 구조를 이용해 최댓값을 빠르게 찾는다는 점이다.

선택 정렬에서는 최댓값 또는 최솟값을 찾기 위해 매 단계에서 남은 배열을 탐색해야 하지만, 힙 정렬은 최대 힙의 루트에 최댓값을 유지한다. 따라서 최댓값을 선택하는 과정과 배열의 위치를 확정하는 과정을 효율적으로 반복할 수 있다.

# 5. 실험 결과 분석

## 5.1 삽입 정렬

삽입 정렬은 이미 정렬된 입력에서 매우 적은 작업만 수행하였다. random 입력에서 입력 크기를 `1,000 → 5,000 → 10,000`으로 늘리면 비교 횟수가 `251,418 → 6,340,103 → 25,224,867`로 증가하였다. `n`이 10배가 되지는 않았지만 비교 횟수가 약 100배 수준으로 증가하는 형태가 나타나 `O(n²)` 특성과 일치한다.

반면 sorted 입력에서는 `999 → 4,999 → 9,999`회 비교로 거의 선형적으로 증가하였다. reverse 입력에서는 `499,500 → 12,497,500 → 49,995,000`회로 증가하여 입력 형태에 따른 차이가 크게 나타났다. 이는 삽입 정렬의 입력 적응성(adaptiveness)을 보여준다.


## 5.2 퀵 정렬

난수 pivot은 정렬된 입력에서 첫 원소 pivot이 만드는 최악 사례를 크게 극복하였다. `n=10,000` sorted에서 Quick-Random은 `162,741`회 비교, Quick-First는 `49,995,000`회 비교를 기록하였다. 가운데 원소와 median-of-three는 각각 `113,631`, `131,343`회였다.

입력 크기 증가에서도 차이가 유지되었다. sorted 입력에서 Quick-First의 비교 횟수는 `499,500 → 12,497,500 → 49,995,000`으로 증가한 반면, Quick-Middle은 `7,987 → 51,822 → 113,631`, Quick-Random은 `10,808 → 76,295 → 162,741`로 증가하였다. pivot 선택이 입력 크기가 커질수록 중요해짐을 확인할 수 있다.

reverse 입력에서는 Quick-Middle이 `119,881`회로 가장 적었고 Quick-Random은 `153,997`회였다. 반면 이번 구현의 median-of-three는 `12,520,005`회까지 증가하였다. 따라서 median-of-three가 항상 다른 방법보다 적은 비교를 보장하는 것은 아니며, pivot 휴리스틱과 partition 결과의 관계를 함께 보아야 한다는 결론이 나왔다. 이 부분에 대해서는 추가적으로 알아보고 싶다고 느꼈다.

duplicates 입력에서는 모든 2-way Quick 구현의 비교 횟수가 크게 증가하였다. `n=10,000`에서 Quick-Random은 `2,568,273`회 비교와 깊이 `543`을 기록하였다. 이는 같은 key가 많은 경우 현재 partition 방식에서 한쪽 구간이 불균형해질 수 있다고 해석된다.


## 5.3 힙 정렬

힙 정렬은 입력 크기가 `1,000 → 5,000 → 10,000`으로 증가할 때 random 입력의 비교 횟수가 `16,869 → 107,606 → 235,155`로 증가하였다. sorted 입력에서도 `17,583 → 112,126 → 244,460`으로 나타나, 첫 원소 pivot 퀵 정렬처럼 입력 형태에 따라 `O(n²)`로 악화되는 현상은 나타나지 않았다.

대신 힙 정렬에서는 여러 번의 swap과 sift-down을 수행하여 이동 횟수가 퀵 정렬보다 큰 경우가 많았다. `n=10,000` random에서 Heap은 `372,312` moves를 기록한 반면 Quick-Random은 `250,360` moves였다.

따라서 힙 정렬은 최악의 경우에도 `O(n log n)`의 시간복잡도를 유지하면서 추가 배열 공간을 거의 사용하지 않는다는 특징을 확인할 수 있었다.


# 6. 세 알고리즘의 종합 비교

세 알고리즘은 서로 다른 장점을 가진다.

- 삽입 정렬은 구현이 단순하고 안정적이며 거의 정렬된 데이터에서 효율적이다.
- 퀵 정렬은 평균적으로 빠르지만 pivot 선택에 따라 성능이 크게 달라진다.
- 힙 정렬은 최악의 경우에도 `O(n log n)`을 유지하며 추가 배열 공간을 거의 사용하지 않지만 안정적이지 않다.

이번 실험에서 특히 확인한 점은 퀵 정렬의 partition 코드는 동일하게 유지해도 pivot 선택만으로 비교 횟수와 재귀 깊이가 크게 달라질 수 있다는 것이다. 강의안에서 random을 pivot 선택에 활용하는 이유가 바로 이 입력 민감도를 줄이기 위한 것임을 실험으로 확인하였다.

또한 입력 크기를 `1,000`, `5,000`, `10,000`으로 증가시키면서 삽입 정렬의 `O(n²)` 증가와 퀵/힙 정렬의 `O(n log n)` 수준 증가가 비교 횟수에 나타나는 것을 확인하였다.

따라서 특정 알고리즘 하나가 모든 조건에서 동일한 특성을 갖는 것이 아니라, 입력 형태, pivot 선택, 안정성 요구, 메모리 조건, 최악 실행시간에 대한 요구에 따라 알고리즘의 특성이 달라진다.

이번 보고서의 수치 비교는 해당 코드와 측정 환경에 한정되며, 특히 실행 시간은 시스템 상태에 따라 달라질 수 있다. 비교 횟수와 이동 횟수는 같은 입력과 같은 코드에서 더 직접적인 비교 기준으로 사용하였다.


# 7. 한계점 및 개선 방향

이번 실험에서는 강의안의 partition 구조를 최대한 유지하고 pivot 선택만 변경하였다. 따라서 결과는 2-way partition과 중복 key 처리 방식의 영향을 받는다.

또한 난수 pivot은 seed를 고정하여 재현성을 확보했기 때문에 실행할 때마다 완전히 다른 pivot 수열을 사용하는 실험은 아니다. 실제 환경에서는 여러 seed를 반복하여 평균과 분산을 확인할 수 있을 것이다.

따라서 다음과 같은 개선사항이 존재한다.

1. 실행 시간뿐 아니라 비교 횟수와 이동 횟수의 증가율을 함께 기록
2. 중복 key 비율을 변화시키고 3-way partition과 비교
3. pivot 선택별 재귀 깊이와 stack 사용량을 더 세밀하게 측정


# 8. 결론 및 고찰

이번 실험에서는 삽입 정렬, 퀵 정렬, 힙 정렬을 동일한 `Record` 구조와 측정 기준으로 구현하고, 퀵 정렬은 난수 / 첫 원소 / 가운데 원소 / median-of-three의 네 가지 pivot 선택 방법으로 비교하였다. 입력 크기도 `1,000`, `5,000`, `10,000`으로 증가시켜 성장률을 관찰하였다.

실험 결과, 첫 원소 pivot은 sorted와 reverse 입력에서 입력 크기가 커질수록 비교 횟수와 재귀 깊이가 급격히 증가하였다. 난수 pivot과 가운데 원소 pivot은 이러한 최악 사례를 크게 완화하였다. median-of-three는 sorted 입력에서 균형 잡힌 분할을 만들었지만 reverse 입력에서는 이번 구현에서 비교 횟수가 크게 증가하여, pivot 휴리스틱의 효과가 입력과 partition 방식에 따라 달라질 수 있음을 확인하였다. 힙 정렬은 입력 형태에 관계없이 `O(n log n)`의 이론적 시간복잡도를 유지하였다.

특히 단순히 실행 시간만 비교하는 것이 아니라 비교 횟수, 이동 횟수, 안정성, 재귀 깊이, 추가 메모리를 함께 측정하고 입력 크기까지 변화시킴으로써 이론적인 복잡도가 실제 증가 형태로 어떻게 나타나는지 확인할 수 있었다.

이번 과제를 통해 정렬 알고리즘은 단순히 데이터를 오름차순으로 나열하는 방법이 아니라, 입력 데이터의 특성과 알고리즘의 구조에 따라 성능 차이가 매우 크게 발생한다는 점을 확인할 수 있었다. 특히 같은 퀵 정렬이라도 pivot을 어떻게 선택하느냐에 따라 비교 횟수와 실행 시간이 크게 달라지는 것이 인상적이었다.

또한 삽입 정렬은 이론적으로 `O(n²)` 알고리즘이지만, 이미 정렬된 데이터에서는 매우 빠르게 동작한다는 점도 확인하였다. 이를 통해 알고리즘의 성능은 단순히 시간 복잡도만으로 판단할 수 없으며, 입력 데이터의 형태도 함께 고려해야 한다는 것을 알게 되었다.

힙 정렬은 입력 데이터의 형태에 관계없이 비교적 일정한 성능을 보였다. 이는 힙 구조를 이용하기 때문에 최악의 경우에도 `O(n log n)` 성능을 보장하기 때문이다. 다만, 안정 정렬이 아니라는 점과 이동 횟수가 상대적으로 많다는 특징도 확인할 수 있었다.

이번 실험에서는 실행 시간뿐 아니라 비교 횟수, 이동 횟수, 재귀 깊이, 안정성까지 함께 측정하였다. 이를 통해 알고리즘을 평가할 때는 단순한 실행 시간뿐 아니라 여러 요소를 종합적으로 고려해야 한다는 점을 배울 수 있었다. 특히 수업 시간에 배운 시간 복잡도 이론이 실제 실험 결과와 유사하게 나타나는 것을 확인하면서 알고리즘 분석의 중요성을 직접 체감할 수 있었다. 앞으로 알고리즘을 선택할 때에 문제의 특성과 입력 데이터의 형태를 함께 고려해야 한다는 점을 배우게 되었다.
